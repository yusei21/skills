# 审查与指令完整性

[English](./REVIEW-INTEGRITY.md) | [Português](./INTEGRIDADE-DE-REVISAO.md) | **简体中文**

本文档定义仓库级策略，用于基于证据的代码审查，以及支持的 AI 编程工具所使用的指令/控制平面变更。

目标是减少误报式审查噪声、保持跨运行时共享行为的可移植性，并防止指令漂移或不安全的能力扩张。

## 审查策略

审查应优先保证正确性和可执行性，而不是追求发现数量。

对于实质性变更，应使用相互独立的审查视角，而不是只依赖一次混合检查：

1. **正确性** — 当前变更引入的具体 bug 或回归。
2. **仓库规范符合性** — 适用的 `AGENTS.md`、`CLAUDE.md`、rules 以及既有项目约定。
3. **上下文/历史** — 当意图不明确时，检查调用方、测试、blame 和针对性历史。
4. **安全性** — 当 diff 跨越安全边界或改变 agent/工具控制平面时执行。

主 `code-reviewer` 已经执行置信度过滤。最终编排应保留这一行为：

- 只报告置信度高于 80% 且可执行的发现；
- 合并根因相同的重复发现；
- 区分当前变更新增的问题与无关的既有技术债；
- HIGH 或 CRITICAL 发现必须包含精确证据和具体失败场景；
- 零发现是完全有效的成功审查结果。

如果某个发现无法明确受影响位置、触发条件和错误结果，则应降级或移除。

## 证据层级

使用验证发现所需的最小证据集合。常用来源包括：

- 修改行及其周围实现；
- 调用方和数据流路径；
- 测试与 fixtures；
- 类型或 schema 约束；
- 适用的仓库指令；
- framework/runtime 的明确保证；
- 对依赖意图的行为使用 `git blame` 或针对性历史。

历史用于澄清上下文，不应凭空创造当前代码和文档中不存在的要求。

## 指令/控制平面变更

以下内容应被视为控制平面资源，因为它们能够改变 agent 的行为或可使用的能力：

- `AGENTS.md`、`CLAUDE.md` 以及更近作用域的指令文件；
- 规范 skills 与 agent prompts；
- rules 和 hooks；
- MCP/工具配置；
- plugin 或 marketplace 元数据；
- `.claude/`、`.codex/`、`.agy/`、`.mimocode/`、`.opencode/`、`.kimi/` 等运行时适配层和兼容内容。

这些文件发生变化时，除了普通文本/代码审查外，还必须执行指令完整性检查。

## 指令完整性清单

当指令或适配层行为发生变化时：

1. 明确受影响运行时的实际优先级，包括根目录与更近作用域的指令。
2. 共享策略保留在规范资源中；原生语法和加载行为放在对应适配层。
3. 比较同级运行时，检查冲突、过期引用、意外重复以及未记录的差异。
4. 不要把某个工具专用指令传播到所有运行时，除非其语义确实可移植。
5. 使用 `skill-security-audit` 检查 prompt injection、意外权限扩张、持久化、凭据访问、不安全的网络/工具配置和外部来源指令。
6. 检查 hooks、MCP servers、scripts 或 plugin 元数据是否实质扩大 shell、文件系统、网络或凭据权限范围。
7. 对有意保留的运行时差异进行记录，避免未来维护者误判为 drift。

## 外部 plugin 与 skill 模式

外部生态可以作为架构和工作流模式的参考。优先把概念适配到本仓库的规范来源模型，而不是整体复制某一工具专用实现。

如果复制或实质性改编了内容：

- 采用前确认上游的准确许可证；
- 保留所要求的通知与署名；
- 按仓库策略记录来源；
- 避免无必要地把共享行为绑定到单一运行时的实现细节。

如果能得到更清晰、更可移植的设计，应优先使用原创措辞和本仓库原生结构重新实现通用工作流模式。

## 与编排流程的集成

`project-orchestrator` 负责识别指令/控制平面任务，并选择相关审计与审查资源。

`orch-pipeline` 负责在提交 gate 之前执行基于证据的审查。标准和大型变更在有价值时应采用独立审查视角，再对结果进行去重和置信度过滤。

预期流程：

```text
检查仓库 + 指令层级
                │
                ├── 实现 / 修改
                │
                ├── 正确性审查
                ├── 仓库规则审查
                ├── 上下文/历史审查（需要时）
                └── 安全/控制平面审查（触发时）
                                │
                                └── 去重 + 置信度过滤（>80%）
                                                │
                                                └── 解决 HIGH/CRITICAL → 提交 gate
```

## 维护规则

如果未来变更降低置信度阈值、移除指令优先级检查，或在适配层中引入第二个实体事实来源，则必须同时记录原因和迁移策略。
